# Caspian-BYOC: a gateway for the user's own config

> Persian edition: [`docs/2026-08-29-design.fa.md`](2026-08-29-design.fa.md).
> The English file is the one the tests read. If the two ever disagree, this
> one is correct.

Date: 2026-08-29
Status: findings, decisions and a build plan. No code is written.

## 1. What this is

A Raspberry Pi that takes a proxy config the user already holds, connects with
it, and shares that connection over WiFi. Other devices join the WiFi and need
no app, no profile and no settings.

The user pastes a share link or drops a QR image into a web panel on the box.
They press one switch. Everything else is automatic.

This project is self-contained. It embeds no servers. It has no relationship to
any other project, shares no code with one, and depends on none. Where this
document cites another program, that program is reference material that was
read, never a dependency.

Not targeting phones has four consequences:

- There is no gomobile binding, no AAR and no xcframework.
- QR arrives as an uploaded image or pasted text, never from a camera. The
  machine running this has no useful camera, and the phone is the thing joining
  the hotspot.
- App store rules never apply.
- The phone clients that inspired this stay references rather than sources.

## 4. Measured facts

Everything here was read from source or produced by a command on 2026-08-29,
then re-checked by a second pass that was told to falsify it. Legal conclusions
are marked as inference, because a licence file states terms and not
conclusions. Anything that could not be settled is marked UNKNOWN with the
command that would settle it.

### 4.1 The engine

xray-core v1.260327.0, licence MPL-2.0.

It links GPL code. `main` reaches `infra/conf`, and
`infra/conf/shadowsocks.go:6` imports
`github.com/sagernet/sing-shadowsocks/shadowaead_2022`, which is
GPL-3.0-or-later. MPL section 3.3 permits distributing the covered software
under that Secondary License, and Xray has not attached the incompatibility
notice to any source file.

INFERENCE, not a measurement: the shipped binary is therefore a combined work
distributed under GPL-3.0. One counter-signal points the other way. The
published Windows archive contains the MPL text and no GPL text, so upstream
does not present it that way. Our licence choice makes the question moot for us.

Linking it into a fresh module was measured, not assumed. A module requiring
only `github.com/xtls/xray-core v1.260327.0`, with no replace directives, builds
and runs: `Xray 26.3.27 started`, socks inbound listening. Binary size 44 MB, or
30 MB with `-s -w`.

Import paths that matter. JSON loading is
`github.com/xtls/xray-core/infra/conf/serial`, function
`LoadJSONConfig(io.Reader) (*core.Config, error)` at `serial/loader.go:72`.
Beware that `common/serial` is a different package with the same name.
Protocol registration is a blank import of
`github.com/xtls/xray-core/main/distro/all`. Lifecycle is `core.New`,
`(*Instance).Start`, `Close`.

Geo data is not embedded. The only `go:embed` in the engine is an HTML file.
`geoip.dat` and `geosite.dat` are read from disk, located by the
`xray.location.asset` environment variable. So any generated config using a
`geoip:` or `geosite:` rule reintroduces a download step. v1 generates no geo
rules.

### 4.2 The TUN inbound, which is how traffic gets in

The engine has a TUN inbound, and it is live in a normal build. This needed
care: `main/distro/all` does not import `proxy/tun`, but `infra/conf/tun.go:4`
does, and `go list -deps ./main` confirms it in the graph. It is registered for
JSON as `"tun"` at `infra/conf/xray.go:37`.

Its entire JSON surface is three fields: `name`, `MTU`, `userLevel`, defaulting
to `xray0` and 1500. No address, no routes, no rules.

On Linux it does exactly three things: opens `/dev/net/tun` with
`IFF_TUN|IFF_NO_PI`, sets the MTU, and brings the link up. There is no
`AddrAdd`, no `RouteAdd`, no `RuleAdd`, and no shelling out anywhere in the
package. It does not even assign an address.

Its own README is blunt about this: enabling it "will result only tun interface
up, and that's it", and warns that a careless default route will "lock your
router up in infinite network loop".

No ICMP. The netstack registers TCP and UDP handlers only. Consequence for the
build: `ping` cannot be the health check.

So the whole of addressing, routing and firewalling is ours:

- an address on `xray0`
- a pinned host route to the user's server via the real gateway, or the tunnel
  tries to reach its own uplink through itself
- a default route, or a policy rule plus a second table
- `rp_filter` handling, or return packets are dropped as martians and the
  tunnel connects while carrying nothing
- INPUT and OUTPUT firewall permits for `xray0`, because a router's own traffic
  is not FORWARD

### 4.3 Why not the redirect path

REDIRECT recovers the original destination on Linux through `SO_ORIGINAL_DST`
and on macOS through pf. On Windows it silently returns an empty destination and
a nil error, so anything built on it looks like it works and does not.

TPROXY is Linux only, and it needs two settings rather than one:
`streamSettings.sockopt.tproxy` and `followRedirect` on the inbound. The gate at
`infra/conf/xray.go:198-199` is also a type assertion to `*DokodemoConfig`, so
no other inbound can ever receive an original destination.

`IP_TRANSPARENT` appears in two engine files, `transport/internet/sockopt_linux.go`
and `proxy/dokodemo/fakeudp_linux.go`. The second is the UDP reply path, which
is the half that makes UDP work.

TUN is chosen because it carries UDP without TPROXY and because it is the only
mechanism that also exists on macOS and Windows for later phases.

### 4.4 The share-link parser

`XTLS/libXray` is MIT. Its `share` package converts share links into an xray
config in Go. It covers `ss`, `vmess`, `vless`, `socks`, `trojan`, `hysteria2`
and `hy2`. It does not cover `tuic`, `ssr`, `wireguard` or `anytls`. It also
accepts raw xray JSON, v2rayN plain and base64 subscription text, and Clash.Meta
YAML.

REALITY coverage is complete: `fp`, `sni`, `pbk`, `sid`, `spx` and `pqv`.

Sizes at v26.3.27: 848 lines for the URI path, 703 for the Clash importer, 494
for the reverse direction, and 1,010 lines of tests over 29 vectors.

It was compiled and run this session against xray-core v1.260327.0. Six vectors,
six passes, REALITY intact.

Vendoring rules that come with the decision to use it.

Take `share` only. Not the gomobile layer, not the base64 request envelope, not
the DNS, geo or controller packages. It is self-contained: standard library, two
xray-core packages, and `yaml.v3`.

Vendor it, do not depend on it. Upstream has already collapsed eighteen exported
functions into one and its README declines to promise stability. Copy the files,
record the exact upstream version beside them, and read later upstream changes
rather than tracking them.

Keep the MIT text and copyright with the vendored files in their own directory.
MIT is compatible with AGPL-3.0-or-later, so the combined work carries our
licence while those files keep their header.

Clear `sendThrough` before building any config. The parser puts the URI fragment
there, and the engine reads that field as a bind address, so `Build()` fails.
Three of three vectors failed in the measurement, including one with no fragment.

Their vectors may be vendored, but they are not our proof. See 4.5.

### 4.5 Why parser tests must assert on the generated config

Not one URI parameter name matches its JSON key:

| URI | JSON key |
|---|---|
| `pbk` | `publicKey` |
| `sid` | `shortId` |
| `sni` | `serverName` |
| `fp` | `fingerprint` |
| `spx` | `spiderX` |
| `pqv` | `mldsa65Verify` |

That table is where the work is, and it is coupled to the engine version, so it
must be rechecked whenever the engine moves.

A URI round trip cannot catch a mapping error, because a parser that misreads a
field re-emits it identically and passes.

The engine's config loader is a useful schema check and a poor completeness
check. Measured over 16 configs: it rejected 9, including a bad REALITY key, a
malformed short id, a missing address and an invalid flow value. It accepted
`sni` in place of `serverName` and silently dropped the value. It accepted a
misspelled top-level key. It accepted port 0. `DisallowUnknownFields` appears
nowhere in the engine.

Worst of the set: `common/uuid/uuid.go:67-83` takes any string of 1 to 30
characters that is not a UUID, and derives a different valid UUID from it with
SHA-1, reporting no error. A truncated id therefore authenticates as somebody
else and presents as "connected but nothing works". The parser must validate the
UUID itself.

### 4.6 The target hardware, measured

A Raspberry Pi 5 with an Ethernet port and built-in WiFi, both currently holding
DHCP leases on the local network.

`nft` 1.1.3 is installed and the live ruleset is empty, so nothing has to be
undone first. The kernel carries `NF_TABLES`, `NFT_NAT`, `NFT_MASQ`,
`NFT_REDIR`, `NFT_QUEUE` and `CONFIG_TUN` as modules.

The built-in radio reports `#{ AP } <= 1` and `#channels <= 1`. An access point
can run beside the existing client link but is pinned to that link's channel,
currently 10. A second access point needs a USB adapter, and none is attached.

UNKNOWN: whether the box runs NetworkManager or dhcpcd. It decides how the
installer configures addresses. Settle it with `cat /etc/os-release` and
`systemctl is-active NetworkManager dhcpcd`.

UNKNOWN: whether the engine's TUN inbound behaves on Raspberry Pi OS arm64 under
systemd-resolved. Never run.

### 4.7 Two interface modes

Mode A: internet on Ethernet, hotspot on the built-in WiFi. Possible today.

Mode B: internet on the built-in WiFi, hotspot on a USB adapter. The adapter
must report AP support. Designed now, measurable when one is attached.

Interface names are never hardcoded. The installer picks an internet interface
and a hotspot interface, and refuses to start when the chosen hotspot interface
reports no AP support.

## 5. The panel

### 5.1 Who uses it

Somebody who received a config from a person they trust and wants the devices in
the room to work. They will not open a terminal, read a log or edit a file.

After install, every action happens in the panel.

### 5.2 Basic mode, which is the default

One screen:

- a switch, on and off
- one status line: connected or not, and which config is in use
- the hotspot name and password, with a QR code so a phone joins by camera
- how many devices are connected
- one button to add a config, by pasting text or dropping a QR image
- one line naming what was detected, for example "Internet: Ethernet. Hotspot:
  built-in WiFi."

Errors are in plain words. "No adapter on this machine can create a hotspot.
Plug in a USB WiFi adapter" is correct. "No AP-capable phy" is not.

### 5.3 Advanced mode

A switch that reveals, and never hides, what basic mode decided: which interface
is which, channel, band and country, the hotspot subnet, DNS behaviour, the
engine log, what happens when the tunnel drops, and the parsed fields of the
config.

### 5.4 Detection, and what happens when it is wrong

The box detects these without asking:

- the internet interface, from the default route
- the hotspot interface, from AP support
- country and channel
- a hotspot subnet that does not clash with the network the box is already on
- the scheme of the pasted config

Two rules keep that safe. Basic mode shows every automatic choice in one line,
and advanced mode can change every one of them. Detection that cannot be
overridden fails silently on the one machine that does not match the assumption.
When detection cannot pick, the panel asks one plain question rather than
guessing.

### 5.5 Privilege

The panel process holds no privilege. A second, small service does routing,
firewall, access point and interface work. They talk over a local socket.

The privileged side accepts a short list of named actions and never a command
built from anything the user typed. A privileged helper that takes a path and an
argument list from its client is not a boundary. It is a way to run anything as
root.

Turning the switch off returns the machine to how it was. The pattern is to
record the inverse of every change as it is made and replay the inverses in
reverse, and it must cover routes, rules and firewall, not routes alone. It must
also survive the process being killed, which means the record lives on disk and
not only in memory.

### 5.6 Where the panel listens

The hotspot interface, always. The local network only if the user turns that on.
Never the uplink. A password is required in every case, on the first screen.

This creates a hazard it does not solve. If the hotspot is misconfigured the
user cannot reach the panel to fix it, and the hotspot interface does not exist
until the access point starts. v1 needs an answer to that.

### 5.7 No external requests

The panel fetches nothing. No CDN, no fonts, no remote script or stylesheet.
Everything is embedded in the binary.

The privacy reason is that a remote asset tells a third party the address of
everyone who opens the panel. The stronger reason is availability: the panel has
to load when the tunnel is down, which is exactly when it is needed.

## 6. Constraints

- The pasted config is untrusted input that ends up in a document handed to a
  privileged network process. Parse and re-serialise. Never interpolate strings.
- No telemetry, no phone-home, no crash upload.
- No Google anywhere, including as a resolver default.
- No code from a GPL application enters the tree. Linking the engine is the one
  deliberate exception, taken with the obligation understood.
- The box fails closed. If the tunnel is down, client traffic does not leave by
  another path.
- Client DNS is answered on the box and resolved through the tunnel. Clients
  with a hardcoded resolver are redirected, not allowed out.
- No secret in the repository, in any file or any commit.
- Nothing is called working without an exit IP captured from real traffic.

## 7. Fail-closed, stated precisely

When the TUN device disappears the kernel drops every route through it, and
traffic falls back to the main table and out of the uplink. So "the engine
stopped" produces a leak by default, not a stop. The block has to be a firewall
rule that does not depend on the interface existing.

Three limits belong in the ruleset rather than in someone's memory. The INPUT
policy must be stated, because a router's own traffic is INPUT and OUTPUT rather
than FORWARD. IPv6 needs its own rules, since `iptables` covers IPv4 only. And
the box's own traffic is outside the guarantee, which is necessary for the
tunnel to work and means the promise covers forwarded client traffic only.

## 8. The build plan

| Step | What | Proof it is done |
|---|---|---|
| 1 | Repo skeleton: module, AGPL-3.0-or-later licence, layout | Builds, licence present, `go vet` clean |
| 2 | Vendor the `share` package with its MIT notice, pinned version recorded | Vendored tests run green in our tree |
| 3 | Adapter: parse a link, clear `sendThrough`, build a config | Field-by-field assertions against the mapping table in 4.5, plus UUID validation |
| 4 | Engine linked, SOCKS inbound, config from step 3 | Exit IP captured through the engine, matched to the address in the user's own link |
| 5 | Clock check before any connect | Refuses to connect and says why when the clock is implausible |
| 6 | TUN inbound plus addressing, routes, `rp_filter`, firewall. No hotspot yet | Box egresses through `xray0`, exit IP captured, teardown restores the box, recovery path tested |
| 7 | Hotspot: interface detection, access point, DHCP, DNS, fail-closed ruleset | Client exit IP captured against a baseline taken first, engine stopped means client traffic stops, no DNS escapes by any port or protocol |
| 8 | Persistence: config, hotspot name and password, panel password, overrides | Survives a reboot with no terminal |
| 9 | Panel, basic mode, privileged split, log redaction | Someone who has not seen it connects using only the panel, and no log or error contains key material |
| 10 | Advanced mode and overrides | Every automatic choice can be changed, and the change survives a reboot |
| 11 | Bad-config recovery | The three failure states are distinguished in plain words: link did not parse, engine rejected it, server did not answer |
| 12 | One-command installer, uninstall included | Clean Pi to working hotspot with no terminal after the install line, and uninstall returns the box |

Changes from the first draft of this plan, all from findings above:

- Clock is its own step and comes before anything that handshakes, because
  REALITY writes the wall clock into the handshake and a Pi has no battery
  clock.
- Persistence is its own step, because step 10's proof assumed it.
- Log redaction joins the panel step, because the engine's own error strings
  print private keys, seeds and short ids.
- Bad-config recovery is a step, because it is the difference between a box the
  user fixes and a box they return.
- Uninstall is part of the installer rather than an afterthought.

Two things every proof from step 4 onward needs, and neither exists yet: a way
to capture an exit IP for this product, and a per-device baseline taken before
the tunnel is up.

### Test material

Step 3 needs realistic URI shapes, including `pqv`, committed as fixtures with
every secret value replaced. Step 4 needs one real server that somebody else
configured, held outside the repository. These are two different needs and one
file cannot serve both.

## 9. Known hazards to design against

**Clock, and it is worse than a handshake problem.** Two separate mechanisms
depend on the wall clock.

REALITY writes the clock into the handshake and some servers check it. A Pi with
no network time has a clock taken from a file timestamp, and the symptom is an
authentication failure the panel will blame on the config.

Worse: which configs the engine ACCEPTS depends on the date. Measured in
xray-core v1.260327.0, `infra/conf/transport_internet.go:709-716`: the
`allowInsecure` option was removed, and the removal is gated on
`time.Now().After(2026-06-01)`. Before that date the engine warns and honours
it. After, it refuses the whole config and tells the user to use
`pinnedPeerCertSha256`, which will mean nothing to them. So a box whose clock
comes up wrong does not merely fail to connect. It accepts a config that the
same binary rejects once the clock is corrected, and the reverse. Config
validity is not a property of the config alone.

Two things follow. The clock check in step 5 runs before validation, not only
before connecting. And a link carrying `insecure=1`, which is the common shape
for a self-signed server, is now a permanent rejection that the panel must word
for a person: the config is not broken, the option it uses no longer exists.

**Log redaction.** Engine error strings embed the private key, the seed, the
short id and the UUID. The most likely user action, pasting a config with a
typo, produces exactly those errors.

**Uplink change.** The pinned host route to the user's server is silently wrong
after a DHCP renewal with a new gateway, an unplugged cable, or a move to
another network. It must be re-derived on uplink change.

**Update path.** The engine is linked in, so an engine security fix is a rebuild
and a reinstall of our binary, by a user who will not open a terminal.

**QR.** Decoding an uploaded image is untrusted image parsing inside the panel
process. Generating one for hotspot join is a second dependency. Both have
licences that interact with the GPL choice.
